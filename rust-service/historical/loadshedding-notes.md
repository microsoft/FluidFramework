
Here is my rough vision for how this works:
1. We provide a way to bound how much inbound writes we have buffered, before we back pressure session writers. This can be done in what ever the simplest way is, but we ideally want to about complicating the important and alredy complex componets like sequencer. This really only has to be accurate for the durable file backend since memory is just gong to use more and more memory regardless and should's block anyway, and buffered has OS buffering we shouldn't try to account for: what ever we do for durable will probably be kinda ok for buffered. This can be fixed configuration of the storage for a document when creating's sea storage object initially to keep things simple, or it could simply report how much is used via a signal of some kind so something upstream could optional use it to produce back pressure (Like a back pressuring session adapter which takes in a signal and uses it to back pressure writes).
2. For writes pending handoff from storage to sequencer, I don't care which capacity they come out of, but I'm guessing having them count against the storage's write memory until sequencer removes them from that hand off space is simplest.
3. We need to bound the size of data we keep for live readers after writes have finished. This means events which have been sequenced, and are either waiting for a live reader to get to them, or sitting in a live read cache, however we manage that. Maybe the simplest design for this is a deq which tracks the the total size used by and the number of readers who still need to send each entry (when a reader becomes live and starts confusing from this, it needs to increment the count for all it still needs to send, and increment the total count of readers so new entries account for it). When items are enqueued, they get the count set to the number of readers that are currently live. Also when enqueuing, the old end can be evaluated to have an item removed if it has no readers needing it and we are full (we can keep extra items with no readers as a read cache for new or non live readers heuristically, but initially we can just use a simple policy of remove it if cache is full and no live readers need it ). If cache is full and we can't remove an entry since readers need it, we simply keep it, exceeding the budget.
4. We ensure we have an per document session factory abstraction, which can be implemented by our network clients, sequencer, and anything which wants to inject decorators around either of these's sessions.
5. We  ensure that such session decorators can close or backpressure session without breaking things.
6. To actually implement a resource use/backpressure/load-shedding policy, we provide a concrete implementation of this decorator factory where each decorator wraps an Arc to a trait which implements the policy (sharing one instance document wide).
7. We write an implementation of the above factory which provides a backpressure signal from the storage, and one from the outgoing read queue (which serves as a read cache as well) to the actual policy logic when building it, constraining the more general policy wrapper factory's policy trait to where it implements new taking in this data.
8. We implement some simply policy trait implementations, like one which balances dropping lagged readers vs backpressuring writers vs refusing new readers with some simple heuristics.
