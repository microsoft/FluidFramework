# Snapshotted Append Stream Research Plan

## Purpose

Build an executable research prototype around the smallest useful abstraction for systems composed of:

- an opaque, totally ordered append stream;
- snapshots generated by clients at known positions in that stream; and
- readers that recover from a snapshot and replay subsequent data.

The core must not depend on Fluid or understand events, users, sessions, framing, or application metadata. Fluid ordering, summaries, reference stream positions, reconnection behavior, and driver APIs will be implemented in separate adapter layers.

The project is intended to test architectural ideas, discover irreducible semantics, and measure performance. It is not initially intended to be production-ready or compatible with every existing Fluid feature.

## Central Question

> What is the smallest composable contract that can provide an opaque, totally ordered, client-snapshotted append stream, and which higher-level service features can be implemented as wrappers over that contract?

## Design Principles

1. Specify behavior before optimizing representations.
2. Keep stream positions opaque. An implementation may use byte offsets, logical ordinals, or replicated log coordinates.
3. Define the kernel for one logical stream. Multiple documents and namespaces belong in a factory or routing layer.
4. Keep appended data and snapshot payloads opaque to the service.
5. Separate required correctness semantics from optional capabilities.
6. Make wrappers obey the same conformance suite as direct implementations.
7. Prefer a small family of focused traits over one trait containing storage, networking, policy, and administration.
8. Add complexity only in response to a demonstrated semantic requirement or measured bottleneck.
9. Push framing, multi-user protocol state, limits, retry policy, and application semantics into adapters whenever practical.

## Initial Kernel

The first API should express these concepts without committing to a particular wire or storage representation.

```rust
trait AppendStream {
    type Position;
    type Append;
    type Error;

    async fn append(
        &self,
        value: Self::Append,
    ) -> Result<AppendReceipt<Self::Position>, Self::Error>;

    async fn read(
        &self,
        after: Option<&Self::Position>,
    ) -> Result<StreamReader<Self::Position>, Self::Error>;

    async fn head(&self) -> Result<Option<Self::Position>, Self::Error>;
}

trait SnapshotStore {
    type Position;
    type Error;

    async fn latest(
        &self,
    ) -> Result<Option<Snapshot<Self::Position>>, Self::Error>;

    async fn publish(
        &self,
        snapshot: Snapshot<Self::Position>,
        expected_parent: Option<&SnapshotId>,
    ) -> Result<SnapshotId, Self::Error>;
}
```

Representative data types:

```rust
enum SnapshotPosition<P> {
    Initial,
    At(P),
}

struct Snapshot<P> {
    includes_through: SnapshotPosition<P>,
    payload: Bytes,
}
```

`SnapshotPosition::Initial` is the distinguished position before any append and allows an initial snapshot whose state includes no stream data. The exact append and reader types will be settled interactively during the foundation phase. The expected common append type is immutable bytes, or a type constrained so implementations can write its bytes directly without interpreting or reframing them.

These signatures are a starting point, not the specification. The behavioral laws below are the stable center of the design.

## Required Semantic Laws

### Append ordering

- Every successful append occupies one contiguous region in a stable total order.
- Concurrent appends may appear in any single order, but their data cannot be interleaved.
- Real-time precedence is preserved: if append A returns before append B starts, A precedes B.
- Reads return committed data in that order without omissions or duplication within the requested range.
- A position is scoped to a stream generation and cannot silently identify data in another stream or generation.
- A successful receipt identifies the committed region and establishes that it is visible to subsequent reads.
- The durability represented by a successful receipt is explicit for each implementation.
- The kernel does not provide event framing or exactly-once retry by default. Adapters may add identifiers, framing, deduplication, and resubmission policy.

### Reading and backpressure

- Reads begin strictly after the supplied position, or at the retained beginning when no position is supplied.
- Readers expose backpressure rather than requiring an implementation to buffer an unbounded stream.
- Cancellation and end-of-current-stream behavior are defined consistently.
- Falling behind retained history produces an explicit error containing enough information to restart from a snapshot.
- The kernel imposes no artificial size or time limits by default. Optional adapters may enforce quotas, chunking, deadlines, and rate limits.

### Snapshots

- A snapshot states the exact committed position whose effects it includes.
- The initial snapshot uses `SnapshotPosition::Initial` and includes no appended data.
- Recovery consists of loading a snapshot and reading data strictly after `includes_through`.
- Publishing a snapshot is conditional on its expected parent or another monotonic precondition, so an older snapshot cannot replace a newer snapshot accidentally.
- The opaque kernel stores snapshot claims but does not assert that client-generated snapshot contents are semantically correct.
- Snapshot publication and any retention decision based on it cannot race in a way that makes the published snapshot unusable.

## Optional Capabilities

Keep the following outside the initial kernel and add focused traits when experiments require them:

- live subscription or efficient tailing;
- stream creation, lookup, deletion, and multi-document namespaces;
- client/session presence and leases;
- retention, reader pins, and pruning;
- external blob storage and content-addressed data;
- authentication and authorization;
- service health, diagnostics, and accounting;
- idempotent retry, deduplication, and resubmission policy;
- size, time, quota, and rate limiting;
- transactional or conditional append beyond one contiguous append;
- snapshot producer election and trust policies.

An optional capability must document whether it can be implemented as a wrapper or requires cooperation from the underlying store.

## Layering Model

```text
Fluid runtime and DDS behavior
              |
Fluid driver and SharedTree adapters
              |
Fluid sequencer: framing, sessions, and reference stream positions
              |
Compression, encryption, transport, caching, replication wrappers
              |
Snapshotted append stream contract
              |
In-memory, file, browser, cloud, and replicated implementations
```

Wrappers may exist on either side of a network boundary. For example, client-side encryption can transform opaque payloads before a network adapter, while storage compression can wrap a server-side implementation.

## Fluid Sequencer Adapter

The `fluid-sequencer` adapter provides the generic multi-user protocol that is intentionally absent from the storage kernel. It will add:

- message framing over the opaque append stream;
- writer identity and per-writer local ordering;
- join and leave events;
- the stream position against which each message was created;
- tracking of the minimum reference stream position across active writers;
- rejection or eviction of writers that fall behind the retained minimum;
- reconnect and resubmission behavior; and
- translation between local submission order, final stream order, and Fluid sequence metadata.

This adapter captures the central Fluid design pattern without making the core storage abstraction Fluid-specific. Applications with pure CRDT events may use the append stream directly or through much thinner framing, while applications whose operations depend on creation context can use `fluid-sequencer`.

## Work Phases

### Phase 1: Interactive foundation

Work interactively to turn the design into a compilable skeleton. Decisions may be made with user guidance as concrete API questions arise; the project does not need a complete up-front specification.

- Create the Rust workspace and establish formatting, linting, build, and test commands.
- Define the core append stream, snapshot, position, receipt, reader, capability, and error types.
- Specify and test contiguous append ordering and real-time precedence.
- Decide the exact byte-oriented append and read interfaces.
- Implement enough of an in-memory reference to validate the traits.
- Establish a conformance-test crate that can be expanded during implementation.
- Stub crates for storage implementations, wrappers, integrations, and demos with their dependency direction encoded in the workspace.
- Record unresolved semantic questions beside the crate that owns them rather than guessing prematurely.

Deliverable: a compiling workspace, an initial tested kernel, a reference path, and crate boundaries suitable for independent Phase 2 work.

### Phase 2: Parallel implementation

After the foundation compiles and its ownership boundaries are stable, multiple agents can implement the remaining crates in parallel. The streams below may proceed concurrently, with conformance tests and integration builds serving as the coordination mechanism.

#### Reference implementation and conformance

- Complete the in-memory implementation with multiple concurrent readers and writers.
- Test append contiguity, real-time precedence, stale positions, snapshots, cancellation, and backpressure.
- Add deterministic fault injection for ambiguous responses and interrupted operations where applicable.
- Add model-based or property-based tests comparing implementations with the reference model.
- Build a native counter example that snapshots and recovers exclusively through the public traits.

Deliverable: a simple correctness reference and an implementation-independent compatibility suite.

#### File-backed implementations

Build two implementations of the same contract with deliberately different durability guarantees.

##### Minimal file implementation

- Implement the shortest practical append-only file store using ordinary buffered file I/O.
- Optimize for understandable code and an early end-to-end demonstration.
- Support normal operation and, if practical, clean-shutdown persistence.
- Do not add checksums, atomic metadata updates, `fsync`, torn-write recovery, or claims of crash durability.
- Fail clearly when stored data is incomplete or invalid rather than attempting recovery.

This implementation is both a learning tool and a baseline for measuring the cost of durability. Its limitations must be explicit in its API capability declaration and documentation.

##### Crash-safe file implementation

- Implement a framed, checksummed append-only log.
- Maintain a sparse mapping between opaque positions and physical byte ranges.
- Define recovery from partial records and corrupted tails.
- Use atomic metadata publication and an explicit `fsync` or group-commit policy.
- Do not acknowledge a durability level stronger than the implementation has completed.
- Add snapshots and retention only after crash recovery is reliable.

Both implementations should share only code that does not obscure the additional logic required for durability. Benchmark them with the same workloads and compare throughput, latency, recovery behavior, implementation size, and conceptual complexity.

Deliverable: an early end-to-end file-backed path plus a separate durable implementation with crash tests and a documented cost comparison.

#### Wrappers and adapters

Develop independently against the conformance suite:

- per-event and block compression wrappers;
- authenticated encryption wrapper with documented nonce and key behavior;
- network-transparent client/server wrapper with end-to-end backpressure;
- in-process cache and optional cache-hint experiments;
- browser storage implementation using an appropriate async browser store;
- `fluid-sequencer` multi-writer protocol adapter;
- Fluid driver using `fluid-sequencer` and a binary protocol;
- direct SharedTree integration with minimal runtime dependencies and a binary protocol;
- public native Rust client API.

Deliverable: evidence about which behaviors compose cleanly and which require changes to the kernel.

#### Demos and performance experiments

- Establish representative workloads before adding platform-specific optimizations.
- Measure throughput, tail latency, memory, startup time, recovery time, disk amplification, and network bytes.
- Measure native and browser bundle size, source lines, dependency footprint, bandwidth, and persisted file size where applicable.
- Compare the minimal and crash-safe file implementations, including source lines, dependencies, persisted size, and the latency/throughput cost of durability.
- Compare independent event compression with block/stateful compression.
- Compare copying with `sendfile` or equivalent zero-copy paths where applicable.
- Evaluate filesystem cache behavior before introducing an application blob cache.
- Investigate `io_uring` only after profiling identifies file I/O submission as a bottleneck.

Deliverable: reproducible benchmark results and decisions tied to measurements.

### Phase 3: Synthesis and architectural review

At the end of each Phase 2 iteration, every implementation, wrapper, integration, and demo agent produces a structured report for Phase 3. Phase 3 synthesizes those reports to evaluate the central abstractions, crate boundaries, implementation scopes, tests, documentation, and measurement quality.

Phase 3 proceeds in this order:

1. Collect and normalize all Phase 2 reports.
2. Separate defects local to an implementation from limitations in shared abstractions.
3. Identify duplicated mechanisms that may belong in a shared crate.
4. Identify shared crates or traits that create unnecessary coupling and may need splitting or narrowing.
5. Compare correctness, complexity, dependencies, bundle and code size, and performance under equivalent guarantees and workloads.
6. Present findings, alternatives, and tradeoffs for interactive review with the user.
7. Make no structural, documentation, or shared-abstraction changes until the user approves the decisions.
8. Apply the approved changes and update tests, documentation, crate boundaries, and shared APIs together.
9. Prepare scoped instructions for each Phase 2 agent or workstream, then begin another Phase 2 iteration.

This loop repeats until Phase 3 finds no justified adjustments and the user agrees that the evidence is sufficient:

```text
Phase 1: interactive foundation
                      |
                      v
Phase 2: implement, integrate, test, and measure
                      |
                      v
Phase 3: synthesize reports and decide interactively
                      |
             changes needed?
                 /       \
              yes        no
                |          |
                v          v
            Phase 2    complete
```

The final Phase 3 still produces a report. It records that no further structural or abstraction changes are justified, summarizes the supporting tests and measurements, and preserves negative or inconclusive findings rather than treating them as failures to report.

### Later advanced experiments

Treat these as separate research branches:

- retention and garbage collection using snapshot reachability and active-reader leases;
- content-addressed blobs and atomic snapshot manifests;
- WebTransport and WASM clients;
- cloud object/blob storage implementations;
- replicated logs, failover, fencing, and quorum acknowledgment;
- a SharedTree-specialized client path;
- cross-event compression state captured in snapshots.

These experiments may discover additional irreducible capabilities. Promote a capability into the kernel only when it cannot be implemented safely as an extension.

## Phase 2 Development Contract

Parallel work begins after Phase 1 provides compiling traits, crate boundaries, and an initial conformance harness. The API need not be final; changes are coordinated through the owning core crate and must keep the workspace compiling. Each implementation or wrapper must provide:

- the contract version it implements;
- its durability and consistency guarantees;
- supported optional capabilities;
- conformance results;
- fault-injection results where persistence or networking is involved;
- benchmark results using shared workloads;
- documented deviations or proposed contract amendments.

Changes to the kernel require a failing test, a concrete use case that cannot be expressed by the current contract, or an unresolved Phase 1 question encountered during implementation.

Phase 2 agents may propose changes to shared abstractions, crate ownership, or project structure, but must not make those changes independently. Shared changes are decided interactively and applied during Phase 3.

### Required Phase 2 report

Each agent or workstream must provide:

- scope completed and deliverables produced;
- tests, conformance checks, integration checks, and fault tests run;
- performance, source size, bundle size, persisted size, and dependency measurements that apply to its scope;
- friction caused by the central traits or neighboring crate APIs;
- implementation-specific workarounds or undocumented exceptions;
- capabilities that could not be expressed cleanly;
- defects that are local to the implementation;
- proposed changes to traits, crate boundaries, factoring, or scope, with alternatives and tradeoffs;
- remaining risks, unfinished work, and confidence level; and
- recommended instructions for the next Phase 2 iteration.

Reports should include reproducible commands and machine-readable benchmark output where practical. A report may recommend no changes; it must still provide the evidence supporting that conclusion.

## Convergence Criteria

The Phase 2/3 loop ends only when the final Phase 3 review and the user agree that:

- all promised capabilities pass the conformance and integration tests appropriate to their declared guarantees;
- no implementation depends on undocumented exceptions or accidental behavior;
- remaining implementation differences and limitations are intentional and documented;
- no report contains a justified unresolved proposal to change the kernel, crate boundaries, or workstream scope;
- documentation describes observed behavior and current architecture rather than only intended behavior;
- benchmarks are reproducible and compare equivalent workloads and durability guarantees;
- correctness, performance, source size, dependency footprint, native and browser bundle size, bandwidth, persisted size, and recovery behavior are covered where applicable;
- comparisons include existing Fluid TypeScript implementations, in-memory versus persisted implementations, and minimal versus crash-safe file implementations where equivalent scenarios exist; and
- negative, neutral, and inconclusive results are retained alongside positive findings.

## Early Research Questions

1. Is one opaque position sufficient, or do commit and physical storage positions need distinct types?
2. What byte-oriented associated append type permits direct file writes while remaining practical for wrappers and network implementations?
3. Should append receipts imply process durability, machine durability, or a selectable durability level?
4. Can snapshot storage remain independent from append storage while preserving atomic publication and safe pruning?
5. Which live-tail semantics belong in the core rather than a polling or notification wrapper?
6. What information must a stale-reader error expose without leaking implementation details?
7. Can all network behavior preserve the same backpressure and cancellation contract?
8. Which guarantees belong in `fluid-sequencer`, and which require cooperation from the generic kernel?

## Initial Non-Goals

- Production deployment or operational support.
- Full Routerlicious or ODSP compatibility.
- High availability in the first implementation.
- Compliance-grade deletion before retention semantics are proven.
- A stable public crate API before the semantic model and conformance tests settle.
- Demonstrating that Rust is faster without comparative measurements.

## Success Criteria

The project succeeds when:

- the semantic contract is small enough to explain precisely;
- the in-memory, minimal file, and crash-safe file implementations pass the portions of the conformance suite promised by their declared capabilities;
- append contiguity and real-time precedence hold under concurrent writers;
- the minimal file implementation provides an early end-to-end path without being mistaken for a durable service;
- the complexity and performance costs of crash safety are measured against the minimal implementation;
- at least one wrapper composes without implementation-specific exceptions;
- the counter example can recover after injected failures;
- `fluid-sequencer` can implement multi-writer framing and reference stream positions without adding Fluid semantics to the kernel;
- a Fluid adapter can identify what it can build above `fluid-sequencer` and what additional capabilities it needs;
- benchmarks provide actionable evidence for or against byte indexing, compression strategies, zero-copy I/O, and caching;
- unresolved limitations are explicit rather than hidden in implementation behavior; and
- a final Phase 3 report demonstrates that the convergence criteria are met and no further adjustments are justified.

The project remains valuable even if an experiment demonstrates that a proposed feature cannot be expressed as a wrapper. Discovering the true boundary of the minimal abstraction is a primary result.
