# Types of Schema Changes

Understanding which types of schema changes are safe versus breaking is crucial for evolving your [SharedTree](../index.mdx) schemas without disrupting existing applications.
Writing a test using <ApiLink package="fluid-framework" api="snapshotSchemaCompatibility">`snapshotSchemaCompatibility`</ApiLink> is highly recommended to ensure any schema changes maintain your compatibility requirements.
Knowledge of the details below will still be needed to design schemas such that the required future changes can be compatible, and to understand any errors detected by the test.

The tables below distinguish two directions of compatibility: [backward compatibility](./index.mdx#backwards-compatibility) (BC) lets a later view use earlier documents, while [forward compatibility](./index.mdx#forwards-compatibility) (FC) lets an earlier view use later documents.
Where viewing requires a schema upgrade, the explanation identifies that extra step; compatibility does not necessarily mean the document can be used as-is.

All the examples below are modifying this schema:
```typescript
class Note extends factory.object("Note", {
    id: factory.string,
    text: factory.string,
    color: factory.optional([factory.string, factory.number]),
}) {}
```

## Compatible Changes

The following changes are [backwards compatible](./index.mdx#backwards-compatibility).
However, it's important that applications carefully review whether the change is [forwards compatible](./index.mdx#forwards-compatibility) inherently or if a [staged rollout](./index.mdx#staged-rollouts) is necessary.

### Adding Optional Fields

BC | FC
---| ---
✅ | ✅ if the older view allows unknown optional fields

```typescript
class Note extends factory.object("Note", {
    id: factory.string,
    text: factory.string,
    color: factory.optional([factory.string, factory.number]),
    height: factory.optional(factory.number), // New optional field
}) {}
```

:::caution
The table's forwards-compatibility result depends on the older clients, not just the new declaration shown above.
Those clients must already enable <ApiLink package="fluid-framework" api="ObjectSchemaOptions.allowUnknownOptionalFields">`allowUnknownOptionalFields`</ApiLink> to tolerate the added field.
Although the option now defaults to `true`, check the settings and library versions of deployed clients before relying on that default.

If it's not already set, then adding a new optional field at the same time as enabling `allowUnknownOptionalFields` is not forwards compatible, since old clients without `allowUnknownOptionalFields` will reject the unknown field.
In that case, a [staged rollout](./index.mdx#staged-rollouts) is needed: first release a version that enables `allowUnknownOptionalFields`, then add the new field in a subsequent release.

```typescript
class Note extends factory.object("Note", {
    id: factory.string,
    text: factory.string,
    color: factory.optional([factory.string, factory.number]),
    // Existing optional fields
}, { allowUnknownOptionalFields: true }) {}
```
:::

This compatibility permits older views to read and edit their declared fields, but not to upgrade documents while omitting the newly added field.
Keep the field in later view declarations if those clients need to perform further schema upgrades.

### Making Required Fields Optional

BC | FC
---| ---
✅ | ❌

**Note**: There is currently no way to make this change in a [forwards compatible](./index.mdx#forwards-compatibility) way.

```typescript
class Note extends factory.object("Note", {
    id: factory.string,
    text: factory.optional(factory.string), // previously required
    color: factory.optional([factory.string, factory.number]),
}) {}
```

### Adding New Allowed Types

BC | FC
---| ---
✅ | ❌

```typescript
class Note extends factory.object("Note", {
    id: factory.string,
    text: [factory.string, factory.array(factory.string)],
    color: factory.optional([factory.string, factory.number]),
}) {}
```

To achieve [forwards compatibility](./index.mdx#forwards-compatibility), staged allowed types can be used to [roll out](./index.mdx#staged-rollouts) support for reading before writing, allowing older clients to read data created with new types.
See [Rolling Out New Allowed Types](./allowed-types-rollout.mdx) for details.

## Incompatible Changes

The following changes remove assumptions that existing clients or documents rely on.
An upgrade can add permissions to the stored schema, but it cannot teach a view to handle a value or missing field that the view no longer supports.
For that reason, preserving existing content in an upgrade candidate is not enough to make these changes compatible.

### Removing Fields

```typescript
// Breaking: Removing field
class Note extends factory.object("Note", {
    id: factory.string,
    // text: factory.string, // REMOVED
    color: factory.optional([factory.string, factory.number]),
}) {}
```

Backward compatibility: this change prevents newer clients from opening documents created with the old schema,
because those documents will have the `text` field, which such clients are not equipped to read,
and require the `text` field on new `Note` instances, which such clients are not equipped to write.

Forward compatibility: this change prevents older clients from opening documents created with the new schema,
because those documents will be missing the `text` field such clients want to read and write.

An optional field differs from this required-field example: a view that allows unknown optional fields may still read an existing document without declaring that field.
However, an upgrade through that view does not retain the omitted field, so the upgrade is rejected rather than removing the field from the document.

### Making Optional Fields Required

```typescript
// Breaking: Making optional field required
class Note extends factory.object("Note", {
    id: factory.string,
    text: factory.string,
    color: [factory.string, factory.number], // Was optional, now required - BREAKING!
}) {}
```

Backward compatibility: this change prevents newer clients from opening documents created with the old schema,
because those documents may not have the `color` field, which such clients are expecting to be populated.

Forward compatibility: an older view still permits clearing `color`, so it cannot use a document whose stored schema requires that field.
It may be able to upgrade the document to make `color` optional again, but this does not solve the new view's inability to read historical documents where `color` is absent.
The change is therefore not safe for a rollout that must continue to support those documents.

### Changing Field Types

```typescript
// Breaking: Changing field type
class Note extends factory.object("Note", {
    id: factory.number, // Was factory.string - BREAKING!
    text: factory.string,
    color: factory.optional([factory.string, factory.number]),
}) {}
```

Backward compatibility: this change prevents newer clients from opening documents created with the old schema,
because those documents will use the `string` type for the `id` field, which such clients read and write as `number`.

Forward compatibility: older clients expect string `id` values and cannot read the numbers permitted by the new document schema.
An upgrade that retained both types would preserve existing content, but the older view would still lack number support.
The upgrade must therefore be rejected rather than treating the larger type set as proof of compatibility.

### Removing Allowed Types

```typescript
// Breaking: Removing allowed type
class Note extends factory.object("Note", {
    id: factory.string,
    text: factory.string,
    color: factory.optional([factory.string]), // removed factory.number
}) {}
```

Backward compatibility: this change prevents newer clients from opening documents created with the old schema,
because those documents can use the `number` type for the `color` field, which such clients read and write as `string`.

Forward compatibility: the older view still allows writing numbers to `color`, so it must upgrade a new string-only document before using it.
Restoring number support can be safe for that older view, but the resulting document is no longer compatible with the narrowed, string-only view.
The ability to perform that upgrade therefore does not make the two application versions compatible collaborators.
