SharedTree schema classes combine runtime values with inferred TypeScript types.
Keep that inference inside your implementation where possible, and deliberately choose the types that cross a package boundary.
See [Reusable Schema Libraries](./schema-libraries.mdx) for choosing what consumers should see.

## Distinguish the export boundaries

Exporting a declaration from a source file does not necessarily make it part of your package's public API.
However, a declaration emitter can still process that file, and an inferred public type can indirectly expose its implementation types.

Identify the runtime values and types reachable from each package entry point.
Publish declarations for those entry points, ensure their imports resolve in the installed package, and test consumers against the package exports rather than source-relative imports.
If you provide several entry points, check each supported one.

Use named public interfaces for domain members and static factories.
Use <ApiLink package="fluid-framework" api="ErasedNode" />, <ApiLink package="fluid-framework" api="ErasedSchema" />, or <ApiLink package="fluid-framework" api="ErasedSchemaSubclassable" /> for an erased schema boundary instead of reproducing the full inferred schema type by hand.
Do not expose SharedTree system types merely because they appear in the declaration output of an internal implementation.

## Understand the compiler options

These options address different problems:

| Option                                                                                  | Purpose                                                                                      | Implication for schema code                                                                                                         |
| --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| [`isolatedModules`](https://www.typescriptlang.org/tsconfig/#isolatedModules)           | Checks restrictions relevant to single-file JavaScript transpilation.                        | Does not itself require explicit types for all exported schema values.                                                              |
| [`isolatedDeclarations`](https://www.typescriptlang.org/tsconfig/#isolatedDeclarations) | Requires enough explicit information to emit declarations without cross-file type inference. | Inferred exported schema values and expression-based exported base classes can require a different boundary.                        |
| [`stripInternal`](https://www.typescriptlang.org/tsconfig/#stripInternal)               | Omits declarations marked `@internal` from emitted declaration files.                        | Can keep implementation-only exports out of declaration output, but does not verify that remaining declarations are self-contained. |

`satisfies` and `as const` help preserve and check inferred types; they are not substitutes for an explicit exported type where `isolatedDeclarations` requires one.
Likewise, `stripInternal` does not remove JavaScript exports or make a runtime member private.

The [isolated-declarations build guide](https://github.com/microsoft/FluidFramework/blob/main/packages/dds/tree/docs/user-facing/isolated-declarations.md) is the detailed reference for two-pass builds, TypeScript versions, declaration-emitter choices, and fallback strategies.
Use it for compiler configuration rather than treating a short configuration fragment as a complete package build.

## Explicitly type the public boundary

This example keeps its schema implementation local while exporting a node type, a schema value, and a static factory.
The erasure helpers are alpha APIs, imported from `@fluidframework/tree/alpha`.

```typescript
import { SchemaFactory } from "@fluidframework/tree";
import { eraseSchemaDetails, type ErasedNode, type ErasedSchema } from "@fluidframework/tree/alpha";

export interface SquareMembers {
	readonly area: number;
}

export type Square = ErasedNode<SquareMembers, "com.example.geometry.Square">;

export interface SquareStatics {
	create(sideLength: number): Square;
}

const schemaFactory = new SchemaFactory("com.example.geometry");

class SquareImplementation
	extends schemaFactory.object("Square", { sideLength: schemaFactory.number })
	implements SquareMembers
{
	public get area(): number {
		return this.sideLength * this.sideLength;
	}

	public static create(sideLength: number): SquareImplementation {
		return new SquareImplementation({ sideLength });
	}
}

export const Square: SquareStatics & ErasedSchema<Square> = eraseSchemaDetails<
	Square,
	SquareStatics
>()(SquareImplementation);
```

Consumers use `Square` as a runtime schema when composing a parent and as a type when working with a node.
They create nodes with `Square.create(3)` and read `area`, without depending on the stored `sideLength` field.
The [schema-erasure tests](https://github.com/microsoft/FluidFramework/blob/main/packages/dds/tree/src/test/simple-tree/api/eraseSchemaDetails.spec.ts) exercise this pattern and its constructor and insertion restrictions.

For a generic factory, explicitly annotate the return type with the public schema type parameterized by the inputs you intend to preserve.
Keep its public node and static interfaces independent of the local implementation class.

See <ApiLink package="fluid-framework" api="FormattedText.FormattedTextSchema" /> and its [implementation](https://github.com/microsoft/FluidFramework/blob/main/packages/dds/tree/src/text/textDomainFormatted.ts) for an example that preserves a scope, formatting schema, and additional atom schemas.

## Adapt an existing build

Apply these options in order, stopping when the result meets your build requirements:

1. Keep schema-dependent operations together and avoid unnecessary file and package exports.
2. Give package exports explicit, focused public types. Keep the full inferred schema type inside the implementation.
3. For file exports used only inside a project, consider `@internal` with `stripInternal`. Verify that no emitted public declaration references a stripped declaration. API Extractor can check release-tag consistency.
4. If explicitly typing the remaining schema exports is impractical, emit declarations for that project with TypeScript without `isolatedDeclarations`. Keep other projects' optimized emission where possible. The detailed build guide explains the resulting dependency ordering.
5. Use pre-generated declarations only when the other approaches do not meet your constraints, and make CI verify that they match the implementation.

Run these checks with your actual declaration emitter.
Do not assume a third-party emitter handles internal tags exactly as TypeScript does.
Keep full type checking as a separate required step if declaration generation uses `noCheck`.

## Test the published contract

Test an installed or packed build of the library, not only its source tree:

-   Compile a consumer that imports the supported package entry point, embeds the schema, constructs nodes, and calls its domain APIs.
-   Check expected type errors, such as access to hidden fields or unsupported construction paths.
-   Enable the compiler options you claim to support, including `isolatedDeclarations` in a consumer that re-exports or specializes the library's schema.
-   Inspect emitted declarations for references to stripped declarations, local source paths, and unavailable dependencies.
-   Exercise runtime imports too. A type-only test cannot detect a missing JavaScript export or a duplicate configured schema class.

For collaboration and persisted data, also run [schema-library compatibility tests](../schema-evolution/testing-schema-upgrades.mdx#testing-schema-libraries).
