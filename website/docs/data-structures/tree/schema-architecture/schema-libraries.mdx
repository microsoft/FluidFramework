A reusable model library has two audiences: code that composes its schemas into a document, and code that uses its nodes.
Design those contracts separately, even if you export them from the same package entry point.
See [Schema Architecture and Libraries](./index.mdx) for choosing an appropriate boundary.

## Choose what to export

A concrete schema class is a good export when consumers need its fields, constructor, and schema information.
Preserve its inferred type rather than annotating it as a broad `TreeNodeSchema`: broad annotations lose information needed for typed construction and insertion.
For collections of allowed types known at compile time, preserve tuple types with `as const`.
Use the [schema definition guide](../schema-definition/index.mdx) for the underlying schema syntax.

When consumers need an embeddable model but should not depend on its stored fields, export:

-   An interface for the node's domain operations and observable state.
-   A node type that retains its SharedTree identity.
-   A runtime schema value for use in a parent's allowed types.
-   Explicit factory methods for constructing nodes without exposing their stored representation.

Use <ApiLink package="fluid-framework" api="eraseSchemaDetails" /> for this pattern.
It returns the same runtime schema with a narrower TypeScript type, retaining the specified instance and static APIs.
It is not a runtime wrapper or an access-control mechanism.
Its API documentation includes a small example and describes why a component root with a required child field can help encapsulate future representation changes.

Use <ApiLink package="fluid-framework" api="ErasedNode" /> to describe the node type and <ApiLink package="fluid-framework" api="ErasedSchema" /> to explicitly describe the exported schema.
Keep the schema identifier literal in that public type aligned with the runtime identifier.
Erasure removes ordinary typed construction from the stored object shape, so retain a domain factory such as `create` or `fromString` in the schema's public static interface.
See [TypeScript and Package Exports](./typescript-exports.mdx) for declaration-emission requirements.

The [schema-erasure tests](https://github.com/microsoft/FluidFramework/blob/main/packages/dds/tree/src/test/simple-tree/api/eraseSchemaDetails.spec.ts) exercise construction, embedding in a view, events, recursion, and compile-time restrictions.

## Make subclassing a deliberate contract

Prefer a non-subclassable export unless consumers need to extend the schema class.
Use <ApiLink package="fluid-framework" api="eraseSchemaDetailsSubclassable" /> and <ApiLink package="fluid-framework" api="ErasedSchemaSubclassable" /> when subclassing is part of your extension model.

Type erasure does not remove internal fields or methods at runtime.
A consumer's subclass can collide with an internal member that its TypeScript type cannot see.
Follow the collision mitigations in the helper's API documentation and document any reserved names.
TypeScript's `private` modifier alone does not provide the runtime isolation of JavaScript `#private` members or non-exported symbols.

Define how consumers construct subclasses.
For example, a static factory implemented with `new this(...)` can construct the derived class, while a factory that names the implementation class always constructs that class.
Its declared return type must also provide the contract you promise to callers; runtime subclass construction does not automatically give an inherited factory a more specific TypeScript return type.
Test both the runtime instance and the exposed type.

## Let consumers configure schemas

Use a factory when consumers supply child schemas, formatting, metadata, or another part of the persisted model.
Pass configuration explicitly instead of mutating a process-wide registry during imports.
For a published factory, document:

-   Which child node behaviors the library requires and which schema kinds it accepts.
-   Which configuration inputs affect stored schema, and which only affect local behavior.
-   How the caller provides a scope and how the library derives identifiers from it.
-   Whether callers can subclass the result, and how they construct nodes.
-   Which combinations of options and child schemas the library supports and tests.

Keep generic parameters that preserve consumer-selected child types through the public API.
Use schema-to-node and schema-to-insertable utilities such as <ApiLink package="fluid-framework" api="TreeNodeFromImplicitAllowedTypes" /> and <ApiLink package="fluid-framework" api="InsertableTreeNodeFromImplicitAllowedTypes" /> rather than substituting plain objects or `any`.
An existing node and the data accepted to construct a node are different contracts.

Create each configured schema once per composition and distribute that result to its users.
Repeated factory calls can create different JavaScript classes even when their schema identifiers match.
Reusing the result avoids mixing those classes in one view schema.
Do not use a single global cache for a factory whose result depends on the consumer's configuration.

### Multiple configurations

Use distinct, stable scopes for distinct model configurations that must coexist in the same document.
For example, an application might configure one text model for headings and another for comments, with different allowed embedded objects.
The application must consistently select the same scopes and compatible configurations when reopening those documents.

A schema identifier is not a serialization of every factory argument.
Using the same scope with different child schemas does not prove that the results are interchangeable.
Treat a change to a configuration used by existing documents as a schema-evolution decision, even if the factory's TypeScript signature is unchanged.
See [Schema Libraries and Versioning](../schema-evolution/schema-libraries.mdx).

## Learn from the built-in domains

These implementations illustrate different boundaries; they are not templates to copy in full.
Some APIs are alpha or beta, and repository source can be newer than your installed release.
Check the API release tags before adopting a pattern.

| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| <ApiLink package="fluid-framework" api="PlainText" />     | A fixed schema exposes text operations and construction without exposing its backing array.                                                                                      | [Implementation](https://github.com/microsoft/FluidFramework/blob/main/packages/dds/tree/src/text/textDomain.ts), [tests](https://github.com/microsoft/FluidFramework/blob/main/packages/dds/tree/src/test/text/textDomain.spec.ts)                   |
| <ApiLink package="fluid-framework" api="FormattedText" /> | A generic factory accepts formatting and extra atom schemas, preserves their types in public members, and exposes a subclassable erased schema with an explicit identifier type. | [Implementation](https://github.com/microsoft/FluidFramework/blob/main/packages/dds/tree/src/text/textDomainFormatted.ts), [tests](https://github.com/microsoft/FluidFramework/blob/main/packages/dds/tree/src/test/text/textDomainFormatted.spec.ts) |
| <ApiLink package="fluid-framework" api="TableSchema" />   | Configurable cell and property schemas are combined with table operations that control structural edits. Different parts of the model expose different amounts of schema detail. | [Implementation](https://github.com/microsoft/FluidFramework/blob/main/packages/dds/tree/src/tableSchema.ts), [tests](https://github.com/microsoft/FluidFramework/blob/main/packages/dds/tree/src/test/tableSchema.spec.ts)                           |

Use the public API docs for the supported contract.
Internal casts, system types, and implementation helpers in these files are not additional extension points for your library.
For recursive extension points, continue with [Composition and Recursive Dependencies](./composition.mdx).
